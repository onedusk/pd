# Changelog

All notable changes to the progressive-decomposition project.

## [Unreleased]

### Added
- **Review phase** (`internal/review/`) — two-pass verification system between Stage 4 completion and implementation start. Go binary runs 5 mechanical checks (producer), then delegates an interpretive triage pass to a separate agent session via A2A (consumer).
- **5 mechanical review checks:**
  - **Check 1: File existence** (`check_existence.go`) — `os.Stat` validation. CREATE+exists→MISMATCH, MODIFY+missing→MISMATCH, DELETE+missing→STALE.
  - **Check 2: Symbol verification** (`check_symbols.go`) — validates symbol refs from task outlines against codebase via graph `QuerySymbols` or file-read fallback. Relocated→STALE, missing→MISMATCH.
  - **Check 3: Dependency completeness** (`check_deps.go`) — finds dependents of MODIFY targets via `GetDependencies(DirectionUpstream)` or import-regex filesystem walk. Unlisted dependent→OMISSION. Direction semantics gated by `TestDirectionSemantics`.
  - **Check 4: Cross-milestone consistency** (`check_crossms.go`) — detects conflicting actions (MODIFY-before-CREATE, CREATE+DELETE), overlapping symbol modifications across milestones. Uses `orchestrator.ParseMilestones` for DAG ordering. Semantic conflicts deferred to A2A interpretive pass.
  - **Check 5: Coverage gap scan** (`check_coverage.go`) — scope-boundary filesystem walk + graph clusters/impact analysis. High recall, moderate precision — interpretive session triages false positives.
- **Stage 3 directory tree parser** (`parse_stage3.go`) — handles both box-drawing characters (`├──`, `└──`, `│`) and plain indentation. Extracts file paths + `CREATE/MODIFY/DELETE (milestone)` annotations. Multiple actions per line supported.
- **Stage 4 task spec parser** (`parse_stage4.go`) — parses `tasks_mNN.md` files. Extracts task IDs (`T-MM.SS`), file+action, depends-on, symbol refs from outlines (backtick identifiers + PascalCase names).
- **Review report formatter** (`report.go`) — markdown output with summary table, per-check findings sections (`R-N.NN [CLASS] \`path\`: description`), and `<!-- INTERPRETIVE PASS NEEDED -->` stub for A2A consumer. `ParseMismatchCount` for implement warning.
- **`decompose review <name>`** CLI command — verifies stages 1-4 complete, opens graph store if available, runs all 5 checks, writes `review-findings.md`, prints summary to stderr.
- **`decompose review-interpret <name>`** CLI command — discovers A2A agents with `review-interpret` skill, submits interpretive triage task with findings + context artifacts. Graceful degradation: A2A available→submit task, not available→print instructions for manual delegation.
- **A2A review-interpret client** (`a2a_interpret.go`) — `SubmitInterpretTask` discovers agents, validates skill, sends `SendMessage` with findings + Stage 1/3/4 files as message parts. `PollInterpretTask` polls until terminal state.
- **`run_review` MCP tool** — single tool running all 5 checks. Registered in unified server alongside decompose tools. Uses `CodeIntelService` graph when available via `SetCodeIntel` method.
- **Two-level implement warning** — `runImplement` checks review state: missing `review-findings.md`→warn; existing with mismatches→warn louder. `--skip-review` flag suppresses.
- **12 review tests** — `TestDirectionSemantics` (gate test), parser tests (tree-chars + plain indent), check tests (file existence, cross-milestone), A2A client tests (mock server, skill validation, error paths).

- **Verification agent + pipeline integration** — "fresh eyes" post-stage verification that catches gaps before they propagate. `VerificationReport` with severity levels (critical/warning/info), 50+ rule-based checks across all 5 stages plus cross-stage coherence rules. Critical findings block pipeline progression in `RouteRange`. Runs automatically after each stage; skip with `--skip-verification`.
- **Verification agent** (`internal/agent/verification.go`) — A2A-compatible agent with `verify-stage` and `verify-cross-stage` skills. Receives only stage output content (never producing agent's context) for "fresh eyes" isolation. Registered as `RoleVerification` in agent registry.
- **Milestone scheduler** (`internal/orchestrator/scheduler.go`) — dependency-aware DAG scheduler using Kahn's algorithm for cycle detection. Thread-safe with `sync.Mutex`. `Ready()`, `MarkRunning()`, `MarkCompleted()`, `MarkFailed()`, `AllCompleted()`. `ParseMilestones()` extracts dependency relationships from Stage 3 markdown.
- **Review gates** (`internal/orchestrator/review.go`) — `ReviewStrategy` interface with three implementations: `CLIReviewStrategy` (terminal prompt), `PRReviewStrategy` (`gh pr create` + poll), `FileReviewStrategy` (sentinel file polling). Select at runtime with `--review-mode cli|pr|file`.
- **Implementation pipeline** (`internal/orchestrator/implement.go`) — coordinates milestone fan-out to parallel Claude Code sessions respecting the Stage 3 dependency DAG. `ImplementerFunc` abstraction enables testing without spawning actual processes. Batch concurrency controlled by `--max-concurrent N`.
- **`decompose implement <name>`** CLI command — verifies decomposition completeness, parses milestones, builds scheduler, selects review strategy, runs implementation pipeline. Each milestone spawns a focused `claude --print` session with Stage 0 + Stage 2 + task spec context only.
- **Implementer agent** (`internal/agent/implementer.go`) — wraps Claude Code CLI as implementation adapter. Composes focused prompts, spawns `claude --print --output-format stream-json --max-turns 50`, collects changed files via `git diff`.
- **Eval framework design** (`docs/internal/eval-framework-design.md`) — design document for empirical evaluation of pd's methodology claims. Defines rubric-based scoring (ambiguity, completeness, file accuracy, clarification count), comparative evaluation, Stage 2 ablation study, and LLM-as-judge extension point.

The Stage 4 parser reads symbol references from backtick-quoted names only, not from bare PascalCase words, so Check 2 and the symbol overlap part of Check 4 see fewer references. See the matching "Fixed" entries for the details.

### Fixed
- **KuzuStore `AssessImpact` direction** — walked `DirectionDownstream` (files the changed file imports) instead of `DirectionUpstream` (files that import it), so `decompose review` Check 5, which runs on the persisted Kuzu graph, reported a changed file's dependencies as "directly affected" instead of its dependents. `MemStore` (used by the `assess_impact` MCP tool) was already correct; a Mem/Kuzu parity test now guards the two against drifting apart.
- **Inverted direction wording** — the `Direction` constant comments (`store.go`), `MemStore.neighbors` comments, and the `get_dependencies` MCP schema description said upstream = "what it depends on". Corrected to match the code: upstream = dependents (who imports this file), downstream = dependencies (what this file imports).
- **Broken doc references** — the CLAUDE.md MCP config example used a non-existent `mcp` subcommand and the wrong config path (`.claude/mcp.json`); it now matches what `decompose init` writes (`.mcp.json`, `--project-root <path> --serve-mcp`), and the README uses the same invocation. CLAUDE.md now points at `docs/process-guide.md`, the tracked `docs/decompose/agent-parallel/stage-1-design-pack.md` (instead of a missing path), and `LICENSE`. The README Contents tree now lists the skill, the binary (`cmd/`, `internal/`), and the `docs/` layout.
- **Silent Stage 4 drift in `decompose review`** — a `tasks_mNN.md` file with no recognizable task headings used to parse to zero tasks, so checks 2-4 reported a false all-clear for that milestone. Review now records a warning in `review-findings.md`, prints it to stderr, and returns it in the `run_review` message.
- **Extensionless files dropped from Stage 3 trees** — unannotated entries like `Makefile` or `LICENSE` were treated as directories. They are now treated as files unless the next line is indented under them.
- **`NextStage` with gaps** — returned the highest completed stage + 1, so stages 0, 1, 3 reported Stage 4 as next. It now returns the earliest missing stage (Stage 0 stays optional).
- **`decompose status <name>` / `decompose export <name>` for unknown names** — printed an all-pending table or empty JSON; both now fail with "decomposition not found".
- **`decompose implement` required Stage 0** — the shared Stage 0 file is optional everywhere else (and the implementer already skips it when absent); the gate now skips it like `decompose review` does.
- **Silent file loss in `build_graph`** — files that were inaccessible, unreadable, or failed to parse were skipped with no signal, as were clusters and edges that failed to persist. Both are now counted and reported on stderr; the `build_graph` response is unchanged.
- **Stage 4 never detected for skill-produced decompositions** — status only looked for `stage-4-task-specifications.md`, but the `/decompose` skill writes Stage 4 as `tasks_mNN.md`. `decompose review` and `decompose implement` therefore refused every skill-made decomposition, and `status`/`get_status` reported Stage 4 as next forever. Stage 4 is now complete when either layout is present.
- **Pipeline runs replaced finished stage files with placeholder text**: `decompose <name>` rewrote existing stage files with stubs, and `decompose <name> 2` wrote a Stage 0 stub because executors guessed the stage as the lowest one missing from the inputs. The requested stage is now passed to the executor, and a run refuses to write a stage file that already exists unless `--force` is set (a full run checks every stage before writing anything).
- **`decompose implement` ran milestones in the wrong order**: `ParseMilestones` read only the first link of a one-line chain (`M1 -> M2 -> M3`), ignored box-drawing arrows (`M1 ──► M2`), and found no milestones in plans made from the skill template, which lists them in the Progress table instead of headings. It now reads every link of a chain, same-line box-drawing arrows, and Progress table rows when there are no headings. A plan with two or more milestones and no dependency arrow at all is refused with an error instead of starting every milestone at once; review Check 4 falls back to the listed milestone order for such a plan. Branches drawn across several lines of ASCII art are still not read.
- **Review Check 1 flagged every file that is created and later modified**: an entry such as `CREATE (M1), MODIFY (M4)` always produced one MISMATCH, on the MODIFY while the file was missing and on the CREATE once it existed. A missing file is no longer reported for MODIFY when the same entry also has a CREATE; CREATE on an existing file is still reported.
- **`run_review` treated an empty graph as a full index**: in a new MCP server session, calling `run_review` before `build_graph` used the empty in-memory store, so every symbol in a MODIFY task was reported as missing from the codebase and checks 3 and 5 found nothing. The in-memory store is now used only when it holds at least one file; otherwise `run_review` uses the graph persisted under `.decompose/graph`, or the filesystem checks when there is none.
- **Review Check 2 gave false and changing MISMATCH results**: the graph lookup fetched 20 substring matches in no fixed order and then looked for the exact name, so a reference to `Store` could be missed in a codebase with more than 20 symbols containing "Store", and the result changed between runs. The lookup now reads up to 100000 matches (the cap `build_graph` persists symbols with) and filters on the exact name, and a symbol found only in other files is reported against the first of them by path. CamelCase words in outline prose such as "TypeScript" or "GitHub" were also treated as symbol references and reported missing; only backtick-quoted names count now, which applies to the symbol overlap part of Check 4 as well.
- **Same-named symbols in one file collapsed into one**: both graph stores keyed a symbol by file path and name, so the three `RequestReview` methods in `internal/orchestrator/review.go` were stored as one (and a direct write of all three to the Kuzu store failed on its primary key). The store key and the Kuzu symbol id now also carry the start line (`filePath:name:startLine`); `SymbolNode.Name` is still the bare name, and `GetSymbol(filePath, name)` returns the first match by start line. `build_graph` symbol counts rise accordingly.
- **A Go import pointed at only one file of the package**: `build_graph` turned every import of a local Go package into a single edge to the first non-test file by name in that folder, so `assess_impact` and upstream `get_dependencies` on any other file of the package found no dependents. A Go import now gives one IMPORTS edge per non-test `.go` file in the imported package folder. Edge counts rise and clusters grow for Go repositories.
- **`get_dependencies` returned function calls and cluster names as files**: the in-memory store followed every edge kind, so a downstream query on a file also returned callee names such as `fmt.Sprintf`, symbol ids, and the name of the cluster the file belongs to, and an upstream query on such a name returned files. It now follows IMPORTS edges only, as the Kuzu store already did; a Mem/Kuzu parity test covers a graph that mixes edge kinds.
- **Running `build_graph` twice in one session doubled the graph**: the in-memory store was never cleared, so a second build appended every edge and cluster again and kept files and symbols that had been deleted since the first build. `build_graph` now empties the in-memory store (new `MemStore.Reset`) after it has checked `repoPath` and before it indexes, so two builds of an unchanged repository report the same stats and a removed file is gone.
- **The persisted graph dropped data without saying so**: `build_graph` copied at most 100000 symbols to `.decompose/graph`, so larger repositories lost the rest, and every CALLS edge was handed to a Kuzu insert that matches two Symbol ids while the extractors store a file path and a callee name, so none was stored and none was counted. Symbols are now copied with no limit, CALLS edges are skipped on purpose, and their count is added to the existing stderr warning. `KuzuStore.QuerySymbols` now reads an empty query as "every symbol" and a limit of zero or less as "no limit", as `MemStore` does; before, either one returned nothing.
- **`build_graph` walked dependency folders**: only `.git` and folders named in the `excludeDirs` tool input were skipped, so in a TypeScript repository every `.ts` file under `node_modules` was parsed and stored. The walk now also skips `node_modules`, `vendor`, `target`, `dist`, and any folder whose name starts with a dot, at every depth below the repository root. The root itself is always walked.
- **Parallel `decompose implement` sessions shared one working tree, and PR mode ran in the wrong folder**: with the old `--max-concurrent` default of 3, each milestone's review listed `git diff HEAD` for the whole tree (so it showed other milestones' files) and two CLI approval prompts could read stdin at once. The default is now 1, in the flag and in the pipeline fallback for a zero value. `PRReviewStrategy` and the commit hash lookup in `decompose review` also ran `git` and `gh` in the current folder; they now run in `--project-root`.
- **`decompose implement` passed the whole prompt as one command-line argument**: the implementer ran `claude --print --output-format stream-json --max-turns 50 -p <prompt>`, and Linux caps a single argument at 128 KB, so a large Stage 0 + Stage 2 + task spec could fail to start. The prompt is now sent on stdin (`claude --print --max-turns 50`). The `stream-json` output was captured into a buffer nothing read; the flag and the buffer are removed.
- **`decompose init` deleted or skipped hook settings and dropped `.mcp.json` keys**: with `--force` the whole `PreToolUse` list in `.claude/settings.json` was replaced, deleting the user's own hooks; without `--force` any existing `hooks` key skipped the install while the run still printed "Setup complete"; and rewriting `.mcp.json` dropped every top-level key other than `mcpServers`. Init now appends its entry to the `PreToolUse` list when no entry runs `.claude/hooks/decompose-tool-guard.sh`, `--force` replaces only that entry (and leaves it alone when it also runs other hooks), a `hooks`, `PreToolUse`, or `mcpServers` value of an unexpected shape is reported instead of overwritten, and other top-level `.mcp.json` keys are kept. `init` now has tests.
- **Tracked config only worked on one machine**: `.mcp.json` was checked in with absolute paths for one machine, and a `docs/decompose` line in `.gitignore` made `git add` skip new decomposition files even though files under that folder are tracked. `.mcp.json` is now untracked and ignored (run `decompose init` to create it locally), and the `docs/decompose` ignore line is removed.
- **Hook queried the graph with grep flags and did nothing without `timeout`**: for a Bash call such as `grep -rn Foo dir` the hook took the first word after `grep` (`-rn`) as the search pattern, so it never found the real one. The Bash branch is removed from `decompose-tool-guard.sh`, and `Bash` is dropped from the matcher that `decompose init` writes and from this repository's `.claude/settings.json`. The hook also calls `timeout`, which stock macOS does not ship; `init` now notes a missing `timeout` the same way it does `jq` (on macOS: `brew install coreutils`). The `.claude/hooks/` copy had drifted from the embedded one and is identical again; a test now compares them.
- **`get_stage_context` always reported `graphAvailable: true`**: the field was a constant, so it was true with no code intelligence service attached and before `build_graph` had run. It is now true only when the attached graph store holds at least one file, the same test `run_review` applies to the in-memory store.
- **`run_review` and `decompose review` treated an empty saved graph as a full index**: a `build_graph` run that matched no files (for example a `languages` filter with no hits) saves an empty graph to `.decompose/graph`, and review then reported every symbol in a MODIFY task as missing. Both now use the saved graph only when it holds at least one file, and otherwise fall back to filesystem checks.
- **Milestones with several sources or prose dependencies got no dependency**: `ParseMilestones` took only one milestone from the left of an arrow and did not read "Depends on:" lines, so `M3, M4 -> M5` lost M3, `M3+M4 (parallel) -> M5` gave M5 nothing, and M4 in `docs/decompose/agent-parallel` had no edge at all. Such milestones were scheduled alongside M1, and review Check 4 reported false MODIFY-before-CREATE findings for them. Every milestone on the left of an arrow is now a source, a parenthesis between the list and the arrow is allowed, and a "Depends on:" line adds dependencies to the last labelled milestone (`M5: Name`). Multi-line branch art (`├──► M4` under an earlier line) and mermaid edges with node labels are still not read.
- **Rust IMPLEMENTS edges vanished from the persisted graph with no warning**: the Rust extractor stores them as type name to trait name, the Kuzu insert matches Symbol ids, and an insert that matches nothing returns no error, so they were neither stored nor counted. `build_graph` now compares the edges it sent with the edges the saved graph holds and adds the difference to the stderr warning. The edges themselves are still not persisted.

### Removed
- **`run_stage` MCP tool**: it ignored its `name` input and, because `--serve-mcp` builds a config with no name or output directory, wrote a Stage 0 stub into the working directory of the server process. The registration, the `RunStage` handler, and its input/output types are gone; `write_stage` covers this path.
- **Unused `NewDecomposeMCPServer` builder**: `internal/mcptools/decompose_mcpserver.go` (`NewDecomposeMCPServer`, `RunDecomposeMCPServerStdio`) was only reachable from a test. The file and that test are deleted; `NewUnifiedMCPServer` is the server `--serve-mcp` runs, and its tool list test stays.
- **Unused `decompose.yml` keys**: `languages`, `excludeDirs`, `templatePath`, and `graphExcludes` were parsed into `ProjectConfig` but nothing read them, so setting them had no effect. The four fields are deleted; `outputDir`, `verbose`, and `singleAgent` remain. A config file that still has the old keys loads as before and the keys are ignored. To skip folders in `build_graph`, pass `excludeDirs` in the tool input.
- **Unused `NewCodeIntelMCPServer` builder**: `internal/mcptools/server.go` (`NewCodeIntelMCPServer`, `RunMCPServer`) was only reachable from `server_test.go`. The file is deleted and its `version` variable now lives in `unified_server.go`; the code intelligence tool tests run against `NewUnifiedMCPServer`, the server `--serve-mcp` runs.

### Fixed
- **IMPORTS edges now persist to disk** — previously all IMPORTS edges had raw specifiers (`./service`, `@dusk/db/queries`) that didn't match any File node in KuzuDB, so they silently failed. With import resolution, 4,161 IMPORTS edges now persist for the Dusk project (2,096 files).
- **KuzuStore upstream query direction** — `fileNeighbors` upstream Cypher was equivalent to downstream (both found what a file imports). Fixed to correctly find files that import a given file.
- **augment.go direction semantics** — swapped `DirectionDownstream`/`DirectionUpstream` usage to match store semantics: downstream = dependencies (what this file imports), upstream = dependents (who imports this file).
- **`longestCommonPrefix` infinite loop** — when prefix was `"a/"` and didn't match, `LastIndex("/")` found the trailing slash and `[:idx+1]` produced the same string forever. Fixed with `TrimRight(prefix, "/")` before `LastIndex`.
- **Clustering O(N*E) performance** — `buildAdjacency` called `GetDependencies` per file (2,096 calls, each scanning 58K edges). Replaced with single `GetAllEdges` pass (O(E)).
- **`persistGraph` aborts on duplicate cluster name** — changed from `return error` to `continue` so persistence completes even with duplicate cluster names.
- **Duplicate hook registration** — removed hooks from SKILL.md frontmatter; `.claude/settings.json` is now the single source for hook config.
- **Hook stderr causing "hook error"** — added `exec 2>/dev/null` at top of `decompose-tool-guard.sh` to silence all stderr from jq, timeout, and KuzuDB.
- **MCP server now exposes all tools on a single stdio connection** — previously, `--serve-mcp` only registered 3 decompose tools (`run_stage`, `get_status`, `list_decompositions`). The 5 code intelligence tools (`build_graph`, `query_symbols`, `get_dependencies`, `assess_impact`, `get_clusters`) were defined but never wired into the stdio server. Now all tools are available through a unified MCP server.
- **`--serve-mcp` capability upgraded from `CapBasic` to `CapMCPOnly`** — the MCP server was hardcoded to `CapBasic`, causing `run_stage` to produce `<!-- TODO -->` stubs even when running as an MCP server. Changed to `CapMCPOnly` so the server operates at its correct capability level.
